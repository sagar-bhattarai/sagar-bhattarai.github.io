# Overview

This lab demonstrates a broken access control vulnerability in a multi-step administrative process. The application checks administrative permissions during the initial step but fails to enforce the same authorization check during the final confirmation step. By capturing and replaying the administrator's confirmation request using a lower-privileged user's session, I was able to perform an administrative action without administrator privileges.

# Question / Lab Objective

The objective was to exploit an access control vulnerability in the application's multi-step user management functionality and gain administrative privileges by bypassing the authorization checks.

![Lab question](/assets/images/writeups/portswigger/access_control/mspwnacoos/1.png)

# Walkthrough

## 1. Exploring the application

After launching the lab, I accessed the target application and explored its available functionality. The website displayed a list of products, individual product pages, and a **My Account** option.

![Initial application page](/assets/images/writeups/portswigger/access_control/mspwnacoos/2.png)

I began by exploring the application to understand its structure and identify potential entry points for testing.

## 2. Logging in as the administrator

I clicked **My Account**, which redirected me to the login page.

The lab provided credentials for two accounts:

- `administrator` - Administrative account.
- `wiener` - Standard user account.

I used both accounts during the investigation because comparing their requests would help me understand how the application handled authorization for different user roles.

First, I logged in using the administrator credentials and accessed the administrative interface.

![Logging in as the administrator](/assets/images/writeups/portswigger/access_control/mspwnacoos/3.png)

After opening the admin panel, I found a user management feature that allowed administrators to change users' roles.

The role modification functionality involved two steps:

1. Selecting a user and initiating the role change.
2. Confirming the action before the application processed it.

I decided to investigate whether both steps properly enforced administrative authorization.

## 3. Understanding the two-step administrative process

To understand how the functionality worked, I selected the user `carlos` and initiated an upgrade from a normal user to an administrator.

During the first step, I selected Carlos and clicked the **Upgrade user** button.

![User management functionality - Step 1](/assets/images/writeups/portswigger/access_control/mspwnacoos/4.png)

The application then displayed a confirmation page asking whether I wanted to proceed with the role modification.

At this stage, I could either cancel the operation or confirm it by clicking **Yes**.

![User management functionality - Step 2](/assets/images/writeups/portswigger/access_control/mspwnacoos/5.png)

This two-step workflow became important during the investigation because the application processed the operation through separate HTTP requests.

I wanted to determine whether the authorization check was performed on both requests or only on the initial step.

## 4. Capturing the administrator's requests

I had Burp Suite running during the administrative operation, allowing me to capture the HTTP requests generated by both steps.

I opened **Proxy → HTTP history** and identified the requests associated with the `/admin-roles` endpoint.

I found two relevant requests:

- The initial request generated when selecting the user and initiating the role change.
- The confirmation request generated when clicking **Yes**.

I sent the relevant requests to **Repeater** so that I could inspect and manipulate them independently.

![Administrator's confirmation request in Burp Suite Repeater](/assets/images/writeups/portswigger/access_control/mspwnacoos/6.png)

The confirmation request contained the following parameters in its body:

`action=upgrade&confirmed=true&username=carlos`

The important observation was that the final confirmation request contained the information required to perform the administrative operation.

I decided to investigate whether this request could be executed using a standard user's session.

## 5. Capturing Wiener's session

Next, I logged out of the administrator account and logged in using the standard user credentials provided by the lab.

I then captured Wiener's authenticated request through Burp Suite and sent it to Repeater.

![Wiener's authenticated request in Repeater](/assets/images/writeups/portswigger/access_control/mspwnacoos/7.png)

I examined the request and identified Wiener's session cookie.

My next step was to determine whether the application would authorize an administrative operation when the confirmation request was submitted using this lower-privileged session.

I considered two approaches.

**Method 1: Constructing a new request**

- Copy the administrator's POST request to `/admin-roles`.
- Keep the confirmation parameters in the request body.
- Replace the administrator's session cookie with Wiener's session cookie.
- Send the modified request to the server.

**Method 2: Replaying the administrator's confirmation request**

- Copy the administrator's captured confirmation request.
- Replace the administrator's session cookie with Wiener's session cookie.
- Preserve the original endpoint, HTTP method, and request body.
- Send the modified request through Repeater.

Both approaches test the same underlying authorization weakness: whether the server validates the user's privileges when processing the final confirmation request.

## 6. Method 1 - Constructing a request with Wiener's session

I initially followed Method 1.

I used the administrator's confirmation endpoint and request parameters but replaced the administrator's session cookie with Wiener's session cookie.

The request was sent to the server through Burp Suite Repeater.

![Method 1 - Modified administrative request](/assets/images/writeups/portswigger/access_control/mspwnacoos/8.png)

The application processed the request successfully, even though it was submitted using the standard user's authenticated session.

This demonstrated that the application was not properly enforcing administrative authorization on the confirmation step.

I attempted to follow the redirect generated by the application, but the subsequent page was restricted because the browser was still authenticated as Wiener.

This was an important observation: successfully executing an administrative action does not necessarily mean that the user has access to every administrative page.

## 7. Method 2 - Replaying the confirmation request

I then tested the second approach.

Instead of constructing a new request, I took the original administrator's captured confirmation request and replaced its session cookie with Wiener's session cookie.

I preserved the remaining request details and submitted it through Repeater.

![Method 2 - Replaying the confirmation request](/assets/images/writeups/portswigger/access_control/mspwnacoos/9.png)

I observed that the application processed the request under Wiener's session as well.

During this test, I observed a role change involving Carlos in the opposite direction from my earlier test. This demonstrated why it is important to verify the exact action and request parameters rather than assuming that every replay produces the same result.

I was again unable to access the redirected administrative page because the active session belonged to Wiener.

**Note:** The exact role-change result depends on the action parameter in the request. An `upgrade` request and a `downgrade` request should not be treated as interchangeable.

## 8. Upgrading Wiener to administrator

After confirming that the authorization check could be bypassed, I decided to test the same vulnerability against Wiener's own account.

I followed Method 1 again, this time modifying the request parameters to target `wiener` instead of `carlos`.

The request was submitted using Wiener's own authenticated session.

![Wiener successfully upgraded to administrator](/assets/images/writeups/portswigger/access_control/mspwnacoos/10.png)

The application processed the request, and Wiener's account was successfully upgraded to administrator.

This was particularly important because it demonstrated that a standard user could modify their own privileges without having legitimate administrative permissions.

## 9. Confirming administrative access and lab completion

After following the redirect, I observed the lab completion message.

I also noticed that the **Admin panel** option appeared in the navigation menu while logged in as Wiener.

![Wiener with administrative access and lab completion confirmation](/assets/images/writeups/portswigger/access_control/mspwnacoos/11.png)

This confirmed that I had successfully exploited the broken access control vulnerability and obtained administrative privileges through the standard user account.

# Key Takeaways

- **Do not trust multi-step workflows:** An application may enforce authorization during the initial request but forget to validate it during subsequent requests.
- **Inspect every HTTP request:** A single user action may generate multiple requests, each of which needs to be examined independently.
- **Understand session cookies:** Session cookies identify authenticated users, but authentication does not automatically grant authorization to perform every action.
- **Test authorization at every step:** Administrative endpoints must verify the user's permissions on every server-side request.
- **Use Burp Suite Repeater:** Repeater allows requests to be modified and replayed, making it useful for testing authorization boundaries.
- **Test self-privilege escalation:** Check whether a standard user can modify their own role or permissions.
- **Distinguish authentication from authorization:** Authentication establishes who the user is; authorization determines what that user is allowed to do.

# Security Impact

This vulnerability allows a lower-privileged authenticated user to perform administrative operations without the required permissions.

In this lab, the authorization check was missing from the final confirmation step of a multi-step role modification process. By replaying the administrator's confirmation request with a standard user's session cookie, I was able to upgrade Wiener's account to administrator.

In a real-world application, this type of vulnerability could lead to:

- Unauthorized privilege escalation.
- Modification of other users' roles and permissions.
- Unauthorized access to administrative functionality.
- Potential compromise of sensitive application data and administrative operations.

The overall severity depends on the application's functionality and the privileges obtained through the vulnerable endpoint.

# Remediation

To prevent this type of broken access control vulnerability:

1. **Enforce authorization on every request:** Verify the user's permissions on the server side whenever an administrative operation is requested.
2. **Validate every workflow step:** Do not assume that authorization performed during the first step remains valid for subsequent requests.
3. **Use role-based access control (RBAC):** Ensure that only users with the appropriate roles can execute administrative operations.
4. **Validate the requested action:** Check the user's privileges, target account, and requested operation before processing role modifications.
5. **Never rely on client-side restrictions:** Hiding buttons or restricting access to confirmation pages does not provide sufficient security.
6. **Log sensitive administrative actions:** Record role changes and other privileged operations to support monitoring and incident investigation.

# Conclusion

This lab demonstrated how an incomplete authorization check in a multi-step administrative process can lead to privilege escalation.

By capturing the administrator's HTTP requests, examining the confirmation step, and replacing the administrator's session cookie with Wiener's session cookie, I was able to execute an administrative operation without the required privileges.

The most important lesson is that authorization must be enforced on every server-side request, not just during the initial step of a workflow. A properly authenticated session should never be sufficient to perform an operation that the user is not authorized to execute.
