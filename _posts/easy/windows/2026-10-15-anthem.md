# Overview

Anthemis a beginner-level Windows room that demonstrates how small information disclosures can lead to access to a machine.

The main challenge is not exploiting a complex vulnerability. Instead, we need to pay attention to the information exposed by the website, inspect its source code, identify the administrator, discover a password hint, and understand Windows file permissions.

## 1. Reconnaissance

I started by performing a full TCP port scan against the target machine.

```bash
nmap -sC -sV -p- -T4 \
-oN /home/kali/Desktop/THM_LAB/rooms/easy/windows/anthem/scan.txt \
<TARGET-IP>
```

### Understanding the command

- `-sC` runs Nmap's default scripts.
- `-sV` attempts to identify service versions.
- `-p-` scans all TCP ports from 1 to 65535.
- `-T4` uses a faster timing profile.
- `-oN` saves the output in normal text format.

The important services to look for are:

| Port | Service | Purpose |
|---|---|---|
| 80/tcp | HTTP | Website enumeration |
| 3389/tcp | RDP | Remote Windows desktop access |

The exact results can vary depending on the target's configuration and scan output.

The web server was the best starting point because we did not yet have credentials for RDP.

![nmap](/assets/images/writeups/anthem/1.png)

## 2. Web Application Enumeration

I opened the target in my browser: `http://<TARGET-IP>/`

The website displayed a blog for Anthem.

Rather than immediately running password attacks, I explored the available pages and looked for information that could help identify users or reveal credentials.

I focused on:

- The homepage and blog posts
- Author profiles
- Page source
- `robots.txt`
- `sitemap.xml`
- Links to other application paths

### Check `robots.txt`

I visited: `http://<TARGET-IP>/robots.txt`

The file contained entries such as:

```text
/bin/
/config/
/umbraco/
/umbraco_client/
```

It also exposed a possible password: `U<REDACTED>!`

This was an important discovery.

![pw](/assets/images/writeups/anthem/possible_pw.png)

**Why does `robots.txt` matter?**

Web crawlers use `robots.txt` to learn which paths a website owner prefers they not crawl. It is not an access-control mechanism. Anyone who knows the URL can read the file.

Developers should never store passwords or other secrets in it.

The `/umbraco/` path also suggested that the website used the Umbraco content management system (CMS).

I kept this information for later use rather than attempting to brute-force the login page.

## 6. Find the Website Flags

The next task was to locate flags hidden throughout the website.

The main lesson is that a flag does not always appear as visible text. It may be embedded in HTML metadata, a text field's placeholder, or an author page.

I checked the following locations.

### Flag 1: The "We are hiring" article

Open the blog post and inspect its HTML source.

Look for metadata and unusual strings in the `<meta>` elements.

The relevant flag is hidden in the metadata of this article.

![flag1](/assets/images/writeups/anthem/flag1.png)

### Flag 2: The search field

Inspect the search field's HTML on the website.

Look for a `placeholder` attribute:

A long placeholder may extend beyond the visible search box, so inspecting the page source is more reliable than looking at the rendered page.

![flag2](/assets/images/writeups/anthem/flag2.png)

### Flag 3: The author profile

Follow the author link associated with the blog.

Inspect the author's profile page and look for the flag displayed there.

![flag3](/assets/images/writeups/anthem/flag3.png)

### Flag 4: The IT department article

Open the article titled: `A cheers to our IT department`

## 7. Connect to the Windows Machine Using RDP

After collecting the website clues, I moved to the final stage of the room.

Nmap had identified RDP on port `3389`.

RDP allows a user to interact with a Windows machine through a graphical desktop. Unlike SSH, it provides a full remote desktop session.

On Kali Linux, I could use FreeRDP:

```bash
xfreerdp /v:<TARGET-IP> /u:<USERNAME>
```
Alternatively

```bash
rdesktop <TARGET-IP> 
```
The tool prompts for the password, depending on the version and configuration.

Use the username format specified by the room. Because this machine is not joined to a domain, do not automatically prefix the username with `ANTHEM\` or another domain name.

Once authenticated, the Windows desktop becomes available.

![rdesktop](/assets/images/writeups/anthem/rdp.png)

## 8. Retrieve `user.txt`

After logging in, I inspected the user's desktop.

The user flag was stored in: `C:\Users\<USERNAME>\Desktop\user.txt`

Open the file and submit its contents to TryHackMe.

This stage confirms that the recovered information was sufficient to gain an initial Windows login.

![user.txt](/assets/images/writeups/anthem/user.txt.png)

## 9. Search for the Administrator's Password

The next question hints that the administrator's password is hidden somewhere on the machine.

Rather than trying to exploit Windows immediately, I followed the clue and inspected the filesystem.

Open File Explorer and enable hidden items:

1. Open File Explorer.
2. Select **View**.
3. Enable **Hidden items**.

Then inspect the root of the C: drive: `C:\`

A hidden backup directory was present: `C:\backup\`

![backup](/assets/images/writeups/anthem/hidden.png)

Inside it, I found a file named: `restore.txt`

However, opening the file resulted in an access-denied message.

![denied](/assets/images/writeups/anthem/permission_required.png)

This is an important distinction: **being able to see a file does not mean that your current account has permission to read it.**

Windows uses NTFS access-control lists (ACLs) to determine which users and groups can access files and what operations they can perform.

## 10. Understand the NTFS Permission Weakness

I inspected the file's security settings.

1. Right-click `restore.txt`.
2. Select **Properties**.
3. Open the **Security** tab.
4. Review the listed users, groups, and permissions.

The file's permissions were misconfigured in a way that allowed the current user to modify the access rules.

This was the key to the next stage.

A normal user should not be able to grant themselves access to a protected administrator credential file unless the permissions or ownership allow it.

### Adjust the permissions in the lab

Using the permissions interface, add the current logged-in user if permitted:

1. Select **Edit**.
2. Select **Add**.
3. Enter the current username.
4. Use **Check Names** to resolve it.
5. Apply the required read permission if the ACL allows the change.

Then reopen `restore.txt`.

The file contained the administrator's password: `C<REDACTED>e`

![admin_pw](/assets/images/writeups/anthem/admin_pw.png)

This is the central privilege-escalation lesson of Anthem: a sensitive credential was stored in a backup file whose permissions did not adequately protect it.

## 11. Log in as Administrator

With the administrator's password recovered, I could access the administrator account through RDP.

Use the target's IP address and the Windows administrator username:

```bash
xfreerdp /v:<TARGET-IP> /u:Administrator
```

Enter the recovered password when prompted.

Once the session opens navigate to: `C:\Users\Administrator\Desktop\`

Alternatively, 

After modifying permission we can view the flag right there.

So navigate to: `C:\Users\Administrator\Desktop\`

The final flag is stored in: `root.txt`

![root flag](/assets/images/writeups/anthem/root.png)

Read the file and submit its contents to TryHackMe.

The room is complete once both user-level and administrator-level objectives have been achieved.
